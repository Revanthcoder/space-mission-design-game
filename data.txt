JUDGE-READY PROJECT SUMMARY
Mission Control is an educational spacecraft-design game that turns mission
engineering into a visible chain of decisions. A player selects a destination,
chooses a compatible mission path, assembles a spacecraft, passes readiness
checks, runs an illustrative flight, responds to events, and receives a
transparent mission report.

The central learning idea:

    EVERY NUMBER IS A DECISION
    EVERY RESULT HAS AN EXPLANATION

The game is designed for a short demonstration, classroom discussion, or
science-outreach activity. It is browser-based, has no account requirement,
and shows both the engineering trade-offs and the limits of the model.

WHY THIS IS A STRONG HACKATHON ENTRY
- Real planetary facts and imagery are used as the context for each choice.
- The game turns abstract systems engineering into an interactive experience.
- The destination-first workflow makes the consequence of a choice visible.
- The scoring engine is transparent: judges can see why points were awarded.
- The report is exportable and useful as evidence of learning, not only a
  final win/lose screen.
- The model labels simplified estimates instead of presenting game values as
  certified NASA flight data.

HOW TO USE THIS FILE
Use the ACCEPTANCE CHECKS to decide whether a spacecraft build passes its
mission path. The VALID-BUILD RANGES show the minimum and maximum values
observed by checking every unique combination of the game's 18 components
that passes all mission checks for that destination.

Each metric range is reported independently. The minimum or maximum for one
metric may come from a different spacecraft build than another metric's
endpoint. Values inside every individual range do not guarantee that a build
passes: all acceptance checks and required system categories must pass
together.

UNITS AND RULES
- Mass: kg
- Cost: game credits (not real-world dollars)
- Power: W; total generation includes scaled solar and radioisotope output
- Available power: total generation minus component power use; must be >= 0 W
- Battery: Wh
- Propellant: kg; these are simplified game reserves, not calculated fuel needs
- Reliability: rounded average component reliability, percent
- Every listed required system category must be installed.
- A component ID can be installed only once.
- Solar output scales by the inverse square of Sun distance. Radioisotope
  output is held at its nominal game value.

turns failure into feedback: the player knows which engineering decision to
change instead of receiving an unexplained rejection.

ACCEPTANCE CHECKS
For each path below, the build must satisfy all of these:
1. Mass is no greater than the listed maximum.
2. Cost is no greater than the listed game-credit budget.
3. Total power generation is at least the listed minimum, and available power
   is nonnegative.
4. Battery capacity is at least the listed minimum.
5. Propellant is at least the listed game reserve.
6. Average reliability is at least the listed minimum.
7. All required system categories are installed.

The score is calculated from the actual simulation result and the selected
configuration. It is not a random end-screen number. The report shows the
category total, the maximum weight, the percentage, and the reason for each
award or deduction.

At selected stages, a mission event can require a decision. A player may
protect reliability, preserve resources, or accept risk for greater science
return. The result is recorded in the mission report.

              |

Measured facts are kept separate from game assumptions. Planetary gravity,
atmosphere, distance, orbital period, and imagery provide context. Credits,
component values, propellant reserves, launch staging, and trajectories are
explicitly simplified for learning.

MODEL LIMITS
These are game-design acceptance ranges, not certified spacecraft limits.
All missions are modeled as Earth departures. The game does not calculate
ephemerides, actual launch dates, transfer trajectories, delta-v, surface
landing, or Earth launch-vehicle performance. The alignment cycles are
approximate orbital alignment periods, not launch windows. Propellant values
are game reserves and must not be used as real mission fuel estimates.

HACKATHON DEMO SCRIPT
Use this sequence for a short judge presentation:

00:00  Start on About and state the one-line promise:
       "Every number is a decision, and every result is explainable."
00:20  Select Mars or Moon and point to the measured facts and path filter.
00:45  Add or remove a spacecraft component and show the resource bars change.
01:10  Select an invalid combination and show the exact readiness warning.
01:35  Correct the design and open Mission Control.
01:55  Run the launch sequence and explain that it is intentionally schematic.
02:20  Resolve one mission event by choosing between safety and science.
02:45  Open the report and show the telemetry graph, scorecard, and reasons.
03:10  End with the educational limitation and the NASA reference panel.

JUDGE TAKEAWAYS
- IMPACT: makes systems engineering understandable in one short browser run.
- CREATIVITY: the destination, path, spacecraft, launch, and report form one
  connected learning loop.
- VALIDITY: source links are visible and game abstractions are labelled.
- RELEVANCE: covers objectives, payload, mass, power, communications, cost,
  launch, mission lifetime, and scientific return.
- PRESENTATION: strong visual language, animated launch, 3D integration,
  responsive UI, charts, and an exportable mission record.

SUBMISSION HONESTY CHECK
Do not present the game values as real launch performance. Say:
"NASA resources inform the vocabulary, facts, imagery, and educational
structure. The playable costs, ranges, trajectories, and propulsion values
are simplified assumptions designed to teach trade-offs."
